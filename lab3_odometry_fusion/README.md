# ЛР3: RF2O + robot_localization EKF

Исходники отдельного адаптера, EKF и веб-интерфейса сравнения. Обычный runtime
подключается к уже работающим драйверам. Опциональный `stationary_sensors.launch.py`
предназначен отдельно для неподвижной инициализации аппаратуры.

`run_on_robot.sh` — launcher для уже подготовленного окружения JetBot, а не
автоустановщик зависимостей. Он требует ARM64 ROS Humble image
`jetbot_lab3_fusion:20261102` и совместимый `ws/install` в этом каталоге. Образы,
сторонние зависимости, результаты сборки и записанные данные в Git не включены.
Скопируйте этот каталог вне `/home/jetbot/IntelligentRobotics`; существующее
развёртывание использовало `/home/jetbot/lab3_odometry_fusion_20261102`.

## Пример неподвижной проверки 2026-11-02

После перезагрузки был запущен наш внешний `stationary_sensors.launch.py` из `/tmp`
существующего контейнера, без mux, клавиатуры, камеры или ArUco. Колёсный контроллер
сначала настроен неактивным; затем проверено, что его единственная командная
подписка — `/lab3/disabled_motor_commands`, а издателей там0. На обычных моторных
топиках подписок0. После этого контроллер активирован для получения энкодерной
одометрии. ROS Twist не публиковался; внутренний драйвер выполняет инициализацию
и собственные нулевые записи скорости. RF2O запущен отдельно с publish_tf=false.

Во время этой проверки интерфейс показывал данные изолированной сессии. Позже
временный запуск был остановлен оператором. Перед новым запуском проверьте текущие
процессы: приведённые результаты не подтверждают их состояние после перезагрузки.
Для перехода из такой временной сессии к обычному управлению оператор выполняет:

```bash
cd /home/jetbot/lab3_odometry_fusion_20261102
bash stop_stationary.sh
# Далее запустите свой обычный teleop.sh в привычном каталоге.
# Затем один RF2O (команда ниже), если он ещё не запущен, и:
bash run_on_robot.sh start
```

`stop_stationary.sh` останавливает наш фильтр и только записанные временные
RF2O/сенсорный launch, сверяя PID, время старта и командную строку. Запись владения
находится в `/tmp/lab3-stationary-owned.json` драйверного контейнера. При несовпадении
скрипт отказывается сигналить процесс: нужно проверить текущее состояние, а не
запускать второй драйверный стек. Он применим только к записанной временной сессии,
а не к произвольному запуску драйверов. После перехода камера/teleop остаются
реализацией исходного репозитория, а фильтр и визуализация — отдельным процессом.

Обычный runtime (`run_on_robot.sh`) не запускает teleop, камеру, ArUco или
аппаратные драйверы и не публикует команды движения. Он использует уже
работающие `/scan`, `/diffbot_base_controller/odom`, `/odom_rf2o` на ROS_DOMAIN_ID=2.
Страница наблюдения не содержит кнопок управления роботом.

## Запуск рядом с существующим teleop.sh

Не запускайте второй экземпляр драйверов. Оставьте обычный teleop-стек работающим.
В другом SSH-терминале робота:

```bash
cd /home/jetbot/lab3_odometry_fusion_20261102
bash run_on_robot.sh start
docker logs --tail 40 jetbot_lab3_fusion
```

При первом запуске/перезапуске оставьте робота неподвижным до появления FUSION LIVE:
адаптер ждёт свежую пару колёсной и лидарной одометрии для начального выравнивания.
Никаких команд остановки или движения он не отправляет.

На ПК, отдельное окно PowerShell; текущий адрес робота может измениться:

```powershell
ssh -N -T -L 127.0.0.1:18084:127.0.0.1:8766 jetbot@<ROBOT_IP>
```

Замените `<ROBOT_IP>` текущим адресом; при проверке это был `10.192.173.147`.
Опция `-o HostKeyAlias=10.103.169.147` нужна только на прежнем ПК, где доверенный
ключ этого робота сохранён под старым адресом. На другой машине используйте свой
проверенный ключ робота; отключать проверку host key не требуется.

Откройте http://127.0.0.1:18084/ . Обычный интерфейс teleop остаётся в другой вкладке.
Страница показывает три траектории, позы/скорости, возраст данных и CSV. Исходный
RF2O также записывается в CSV под именем `raw_lidar`, без изменения его координат.
Clear visible trails очищает только рисунок браузера, не одометрию и не фильтр.
Кнопки Wheel arrow / RF2O arrow / EKF arrow над графиком независимо скрывают и
показывают стрелки направления. Траектории, показатели и сбор данных продолжаются.
Переключение действует в этой вкладке; после перезагрузки страницы все стрелки
снова включены.

```bash
bash run_on_robot.sh status
bash run_on_robot.sh restart  # только наш адаптер/фильтр, новая сессия выравнивания
bash run_on_robot.sh stop     # только наш адаптер/фильтр; не останавливает робота
```

При перезапуске колёсного/RF2O источника, скачке времени или разрыве одометрии
наша сессия останавливается: после восстановления источников запустите её снова
на неподвижном роботе. Не добавляйте ещё один EKF поверх существующего.

## Что объединяется

`params/ekf.yaml` — реальная конфигурация Humble `robot_localization`, planar EKF:

| Вход | Используемые величины | Топик адаптера |
|---|---|---|
| Колёсная одометрия | vx, vy=0, угловая скорость z | `/lab3/ekf/wheel` |
| RF2O | x, y, yaw | `/lab3/ekf/lidar` |
| Результат EKF, 20 Гц | сглаженная поза и скорость | `/odometry/filtered` |

Одновременно не используются положение и скорость одного и того же источника:
они коррелированы. `vy=0` — допущение отсутствия бокового скольжения дифференциальной
платформы, с ненулевой дисперсией. `use_control=false`: EKF не получает управление.

Существующий колёсный драйвер сохраняет единственный TF `odom → base_footprint`.
У RF2O и EKF `publish_tf=false`; фильтр работает как отдельный источник одометрии
для сравнения. Это не замена TF всей навигационной системы.

RF2O использует `/scan`, `base_frame_id=base_footprint`, `odom_frame_id=odom`,
`init_pose_from_topic=/diffbot_base_controller/odom`, `publish_tf=false`.
Этот начальный топик не является непрерывным комплексированием.

Если после перезагрузки RF2O не запущен, запустите ровно один экземпляр в уже
настроенном драйверном контейнере (не одновременно с другим launch RF2O):

```bash
docker exec -it jetbot_ros2_mipt_rviz-jetbot_educational-1 bash
source /opt/ros/humble/install/setup.bash
source /home/app/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=2
ros2 run rf2o_laser_odometry rf2o_laser_odometry_node --ros-args \
  -p laser_scan_topic:=/scan -p odom_topic:=/odom_rf2o -p publish_tf:=false \
  -p base_frame_id:=base_footprint -p odom_frame_id:=odom \
  -p init_pose_from_topic:=/diffbot_base_controller/odom -p freq:=10.0
```

Имя контейнера здесь — проверенное 2026-11-02; перед запуском проверьте `docker ps`.
Этот шаг не запускает моторы, однако требует уже работающих драйверов скана и TF.

Наш адаптер вычисляет один раз `A = T_wheel(t0) * inverse(T_rf2o(t0))` по близкой
по времени неподвижной паре и выдаёт `A * T_rf2o(t)`. Дальнейшего подгона под колёса
нет. Исходное расхождение отображается отдельно; оно могло включать прошлый дрейф,
поэтому новое выравнивание не доказывает точность предыдущего заезда.

RF2O обычно выдаёт нулевые ковариации. Адаптер задаёт положительные стартовые
дисперсии: lidar xy=0.0025 м², yaw=0.0064 рад²; wheel vx=0.001, vy=0.0025,
vyaw=0.01 в соответствующих единицах. Эти значения — настраиваемые предположения,
не результат калибровки. Лидарная XY-ковариация изотропна и не меняется при вращении.
Временные метки сохраняются, старые/будущие данные отбрасываются;
`smooth_lagged_data=true`, история 2 с учитывает задержку обработки скана.

Для медленной платформы задана явная диагональная process_noise_covariance:
Qx=Qy=Qyaw=1e-4, Qvx=Qvy=0.01, Qvyaw=0.02, остальные диагональные элементы также
положительные. В отличие от больших стандартных шумов прямого изменения позы,
это сильнее опирается на модель движения через измеренные скорости. Настройка
предварительная; она сглаживает/задерживает лидарную коррекцию и не является
способом устранить медленный систематический дрейф. На операторских заездах нужно
проверить задержку в поворотах и конечную ошибку, а не только гладкость графика.

Фильтр может продолжать предсказания после потери датчика. Поэтому важен индикатор
здоровья обоих входов, а не только поступление `/odometry/filtered`. При потере
входа страница помечает результат PREDICTION ONLY, а не успешное комплексирование.

## Проверка без движения

```bash
python3 /home/jetbot/lab3_odometry_fusion_20261102/validate_live.py \
  --duration 30 --output /home/jetbot/lab3_odometry_fusion_20261102/results/stationary.json
```

Это только чтение HTTP. Отчёт содержит частоты, начальную/конечную позу, дрейф,
ковариации, TF-рёбра и диагностику. Статический тест не доказывает, что EKF точнее
каждого отдельного источника при движении.

Для количественного сравнения оператору нужно вернуться в отмеченную физическую
точку после 1 и 3 кругов и сохранить CSV. Для каждого источника сравнивают
`hypot(x_end-x_start, y_end-y_start)` и нормализованное изменение yaw. Нужна одна
непрерывная сессия без перезапуска драйверов/RF2O/фильтра. Команды движения выполняет
только оператор. Проверка TF и достаточной точности колёсных заездов ранее отмечена
пользователем как выполненная; численные результаты тех заездов сюда не придуманы.

## Сборка и происхождение

Используется существующий ARM64 ROS Humble образ `jetbot_full_ros2` плюс
`libgeographic-dev` в ОТДЕЛЬНОМ контейнере сборки. Сборка/установка сохраняются в
`/home/jetbot/lab3_odometry_fusion_20261102/ws`, runtime-образ —
`jetbot_lab3_fusion:20261102`. В runtime нет устройств, Linux capabilities;
корневая файловая система и исходники доступны только для чтения. Драйверные
контейнеры не пересоздаются. Автозапуск не включён.

Источники: robot_localization humble-devel commit
`8696ee5a9e4f959fcaae37835dcf2ed12ead581b` (3.5.4), geographic_info ros2 commit
`f70b81a438172cd7a066dc1b18314d70e0eb6389` (только geographic_msgs).

Команда сборки внутри отдельного контейнера с установленным GeographicLib:

```bash
source /opt/ros/humble/install/setup.bash
MAKEFLAGS=-j1 CMAKE_BUILD_PARALLEL_LEVEL=1 colcon --log-base /lab3/ws/log build \
  --base-paths /lab3/ws/src --build-base /lab3/ws/build --install-base /lab3/ws/install \
  --packages-select geographic_msgs robot_localization --executor sequential \
  --cmake-args -DBUILD_TESTING=OFF -DCMAKE_BUILD_TYPE=Release \
  '-DCMAKE_CXX_FLAGS_RELEASE=-O1 -DNDEBUG -g0' '-DCMAKE_C_FLAGS_RELEASE=-O1 -DNDEBUG -g0'
```

После смены образа/версии ROS нужна повторная совместимая сборка. Не переносите
ARM64 бинарники на Windows/x86. Локальные исходники и конфиг сохраняются отдельно
в `C:\data\MIPT\robotics\lab3_odometry_fusion`.
